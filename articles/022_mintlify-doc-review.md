## はじめに

AI にコードを書かせる機会が増えて、次は仕様書まで任せるようになりました。便利なのですが、レビューがまったく追いついていません。

Pull Request が何件も並ぶと、正直、もう見ていられなくなるんですよね。差分を開くたびに、どこから手をつけるべきか悩む時間のほうが長い気がします。

レビューが滞ると、確認が甘くなったまま次のタスクに進んでしまうこともあります。量に押されて丁寧さが後回しになっていく感覚は、なるべく避けたいところです。

輪をかけて厄介なのが、AI が吐き出す Markdown ファイルそのものです。白黒の見た目で目が滑ってしまい、ドキュメント用のフォルダにファイルがずらっと並んでいるだけでは、なかなか開く気になりません。

そんな中で見つけたのが、Markdown を整った Web ページとして表示してくれる [Mintlify](https://mintlify.com) というサービスです。導入するだけでレビューの負荷がぐっと下がったので、今回はその話を共有します📚

## Mintlify を入れると何が変わるか

Mintlify は、もともとドキュメントサイトを自動で作るためのサービスです。Markdown で書いたファイルを渡すだけで、そのまま整った Web ページとして表示してくれます。

ドキュメント用のフォルダに Markdown ファイルを並べておくだけで、見出しやコードブロックがきれいにレイアウトされた状態で出てきます。導入の手間はほとんどありません。

これが思いのほか効きます。同じフォルダでも、エディタでファイル名がずらっと並んでいるのを見るのと、整形されたページとして表示されるのとでは、読み始めるまでの心理的なハードルがまるで違います。

中身は 1 文字も変えていないのに、開く気になるかどうかがはっきり変わってきます。後回しにしていたドキュメントを、気づけば普通に開くようになっていました。

驚いたのは、1件あたりを読む時間そのものはさほど変わらなかったことです。変わったのは、開くまでの助走の短さでした。開く回数が増えれば、結果としてドキュメントに触れている時間の総量も自然と増えていきます。

## なぜ HTML ではなく Markdown なのか

ここが今回いちばん言いたいところです。

最近は、AI に直接 HTML を出力させてドキュメントを作る、という話もよく聞きます。見た目まで一気に仕上がるので魅力的に見えますが、個人的にはあまりおすすめしません。

まず、生成のたびにデザインが変わってしまいます。AI が毎回違うレイアウトの HTML を吐き出すので、読む側は内容に入る前に、まず今回のレイアウトを読み解くところから始めることになります。見出しの付け方も強調の仕方もそのつど違うので、なかなか慣れません。

これでは、本来向き合うべき中身になかなかたどり着けません。ドキュメントを読む目的は内容を理解することであって、レイアウトを解読することではありません。コードのレビューなら差分だけを見ればいいのに、HTML では見るべき対象がひとつ増えてしまいます。

もう一つ、タグの分だけ入力も出力も長くなり、トークンを余計に消費します。`<div>` や `<span>` を書かせるだけで、AI にとっても読む側にとっても文字数が膨らんでいくわけです。ちりも積もればで、意外とばかにならないコストになります。

Markdown であれば、AI が触るのは文章の構造だけで済みます。見出しやリストといった骨組みさえ書けば、見た目は Mintlify 側が常に同じ形で与えてくれるので、デザインは毎回変わりません。

デザインが一定であれば、どこに何が書いてあるかを探し直す必要がなく、内容そのものに集中できます。前回読んだページと、同じ場所に同じように情報が並んでいます。この安心感は、思っている以上に大きいです。

要するに、この役割分担さえ成り立てば、道具は Mintlify でなくてもいいはずです。**AI は構造だけを書き、見た目は道具に任せます**。この線引きこそが、レビューの負荷をだいぶ軽くしてくれます。

## レビューの流れがどう変わったか

実際に、レビューのやり方そのものも変えました。Pull Request の差分を 1 行ずつ追いかける代わりに、ドキュメントを主軸に置くようにしています。

大事なところはドキュメントを読んで押さえ、細かい実装の妥当性は AI に任せています。細かいところまで自分の目で追う体力は、さすがに残っていません。

有料プランでは、ブランチごとにドキュメントのプレビューを作れます。Pull Request を出すタイミングでドキュメントも一緒に更新しておけば、そのブランチのプレビューを開くだけで変更の全体像がつかめる、という仕組みです。

コードの差分を延々と読むよりも、まとまった説明を 1 つ読むほうがずっと速いです。実装の細かいところはどうせ AI が書いたものなので、そこは信頼して任せてしまうという判断です。

無料プランでも、ローカルでプレビューを起動することはできます。同じ Wi-Fi につながっていれば、パソコンで動かしたプレビューをスマホから見に行くこともできて、ちょっとした確認には十分です。パソコンの前に戻らなくても様子を見に行けるのは、地味にありがたいポイントです。

ブランチごとのプレビューはあくまで有料プランの機能なので、チーム全体で乗り換えるのはもう少し先になりそうです。とはいえ、選択肢のひとつとして持っておく価値はあると思っています。

## おわりに

発表のあとの雑談で、参加者から「見やすくすることも大事だけど、それ以上にドキュメントを最新に保つ仕組みのほうが大事ですよね」という指摘をもらいました。

まったくその通りだと思います。見た目を整えても、中身が古ければ意味がありません。ドキュメントを CI/CD で常に最新化する仕組みがあってはじめて、Mintlify による見やすさが生きてきます。

見た目を整える工夫は、今日からでもすぐに始められます。ドキュメントを更新し続ける仕組みのほうは、もう少し地道な積み重ねが要りますが、土台としてはそちらのほうが効いてくるはずです。

読みやすさと最新さ、この両方が揃ったときに、ドキュメントを主軸にしたレビューの進め方は完成するのだと思います。ぜひ、見やすさと最新化の仕組みはセットで整えていきたいですね😉
